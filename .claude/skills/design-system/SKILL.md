# Дизайн-система КТМ — ресерч и ревью вёрстки

Правила этого сайта выстраданы в переписке и стоят дорого: каждое из них появилось после
того, как что-то «ебнулось» на экране. Скилл нужен, чтобы они применялись до правки
(ресерч существующих паттернов) и проверялись после (ревью), а не всплывали скриншотами.

## Когда применять

**Применять:**
- новая страница или новая секция;
- перевёрстка существующего блока (плашка → текст, аккордеон → список, смена сетки);
- любая правка, затрагивающая больше одного файла: кегли, отступы, цвета, плашки, кнопки;
- рефакторинг стилей, вынос дублей, чистка мёртвого CSS;
- запросы вида «приведи к нашим правилам», «проверь вёрстку», «почему тут широко/криво».

**Не применять:** правка одного значения в одном месте (поменять текст, подкрутить один
отступ, заменить одну ссылку). Там скилл — оверхед.

## Источник правды

1. `C:\Users\User\.claude\CLAUDE.md` — общие правила пользователя: плотность набора,
   мера строки, перечисления, контраст текста, отступы через токены, вьюпорт ~1280 CSS-px.
2. `CLAUDE.md` в корне проекта — правила этого сайта: палитра, плашки, кнопки, чипы,
   иконки, FAQ, выравнивание, шкала кеглей.
3. `src/styles/tokens.base.css` + `tokens.semantic.css` — значения. **Читать их, а не
   помнить**: шкала и токены меняются, память устаревает.

`references/checklist.md` в этом скилле — рабочий чек-лист с сигнатурами нарушений и
разбором ловушек, на которые уже наступали. Читать его целиком перед ревью.

## Процесс

### Фаза 1. Ресерч (до правки)

1. Прочитать оба `CLAUDE.md` и файлы токенов — актуальные значения шкалы, меры, плашек.
2. Найти **готовый паттерн** для задачи и повторить его, а не изобретать:
   - editorial-список с номерами → `src/components/sections/PlanSteps.astro`;
   - чек-лист (галочка + заголовок + пояснение) → `src/pages/onkomarkery.astro`, `.prep-list`;
   - FAQ (статичный, две колонки) → `src/components/sections/Faq.astro`;
   - ряды без плашек на тёмном полотне → `src/components/sections/HowWeTreat.astro`;
   - карточки-ссылки → `.next-card` в `onkomarkery.astro`;
   - градиентная плашка с белыми карточками внутри → `.rel-tile` в `s-chego-nachat.astro`.
3. Прогнать `node .claude/skills/design-system/scripts/check-design.mjs` **до** правки —
   зафиксировать исходное число нарушений, чтобы не приписать себе чужие и не внести новых.
4. Проверить, нет ли того же кода в нескольких страницах: шапка, футер, кнопки, чипы
   дублируются исторически. Правка в одном месте без остальных = рассинхрон.

### Фаза 2. Правка

- Кегли — только токенами шкалы, свой `clamp()` не писать.
- Мера — токеном `--measure-*` **на самом текстовом элементе**, не на контейнере.
- Отступы — `--s-*`, вертикальный ритм — `--section-gap` / `--head-gap`.
- Цвета — семантические токены; hex в страницах запрещён.
- Новый визуальный приём не придумывать: дизайн-система зафиксирована.

### Фаза 3. Ревью (после правки)

1. `node .claude/skills/design-system/scripts/check-design.mjs` — печатает нарушения с
   путём, строкой и подсказкой; код возврата 1, если что-то найдено. **База сейчас — ноль
   нарушений**, поэтому любое срабатывание после правки внесено этой правкой. Флаг `--json`
   — машинный вывод.
2. `npm run build` — сборка должна быть чистой.
3. Пройти глазами по `references/checklist.md`: часть правил (одинаковость плашек в ряду,
   «мера после снятия плашки», роли ступеней шкалы) скриптом не ловится.
4. В ответе пользователю: что изменено, какие правила применены, что осталось спорным.
   Если правило пришлось нарушить — сказать прямо и объяснить, а не молча оставить.

## Ловушки, на которых уже наступали

Полный разбор — в `references/checklist.md`, здесь коротко:

1. **`ch` считается от кегля элемента.** Мера на контейнере-обёртке (16px) даёт совсем не
   ту ширину, что на заголовке 42px. Токен заголовка на h3 22px сжимает его в столбик.
2. **Снял плашку — верни меру тексту.** Пока текст жил в узкой плашке, меру задавал
   контейнер; без плашки та же строка растягивается на 1180px.
3. **Проценты для меры** (`max-width: 70%`) считаются от случайного родителя — запрещены.
4. **Две «белизны» рядом** (`#fff` и `#fafdff`) читаются как «плашка полупрозрачная».
5. **Hover, меняющий рамку/фон карточки**, в ряду одинаковых плашек читается как «другая
   плашка». Красить только ссылку/заголовок внутри.
6. **Значения в px/em вместо знаков.** `720px`, `60em` — это 84–125 знаков в строке, то
   есть «без меры». Прикидывать знаки, а не пиксели.
7. **Вьюпорт пользователя ~1280 CSS-px** (Windows 150%). Правки шире этого он не увидит;
   его скриншоты — в физических пикселях, делить на 1.5.

## Проверка на живой странице

Порт зафиксирован: `npm run dev` → `http://localhost:4330`. Если порт занят — сервер уже
запущен, не поднимать второй. Скриншоты пользователя — основной канал проверки: после
крупной правки просить обновить конкретный экран, а не «сайт целиком».
